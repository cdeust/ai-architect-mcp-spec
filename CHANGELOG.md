- A delivery gate (`pnpm gate`, `scripts/gate/`): a commit is judged before it is pushed, by its tests and by mutation testing of the lines it touches. `delivery-gate.json` lists the checks (build, the unit suite with coverage, perf, the Python suites of `scripts/tests`, each a list of arguments), what counts as production code, the ignored directories a run takes from the worktree (`carry`: `node_modules`), and what the guard of the session refuses; `stryker.config.json` configures Stryker (10.1.1, pinned, with the Vitest runner on the `forks` pool: the `threads` pool crashes on the native SQLite module). The gate refuses work that is not committed, and reads the commit and the base once, at its start: the copy, the diff and the verdict are of those two. It writes the committed tree, each file as git stores it (no checkout, so no filter of the machine runs; links last, so no file is written through one), into a directory of its own beside the verdicts in the git directory, runs everything there and removes it: the worktree is never written, so the verdict is for the tree the checks ran on and nothing a check wrote stays behind. Stryker mutates the production files the commits add or modify whole, and the gate judges the mutants whose span overlaps a changed line, so an expression written on several lines is judged when one of its lines changed. A mutant passes when a test saw it (killed, timed out, or the mutated code did not load or compile) or when the line above marks it `// Stryker disable next-line <Mutator>: equivalent: <why>`; a mark without that reason, a survivor, an uncovered or an unfinished mutant and any status the gate does not know fail it, and so does a changed file that turns mutation off for more than one line. A file name the mutation tool would read as a pattern or a list is refused. The verdict is recorded under the git directory, by the hash of the tree; it names the hash of the gate that wrote it (code, configuration, profiles). Three layers. (1) Each operation runs in a sandbox of its own (`@anthropic-ai/sandbox-runtime` 0.0.83, pinned) under the profile the configuration names for it: `scripts/gate/profiles/offline.json` (build, perf: no network) or `loopback.json` (unit, mutation testing: the loopback the tests' servers need, which on macOS is every local port). Both write the directory of the run and nothing else, and read nothing of the user's home but that directory, the files of the gate that judges and the tools (the directories of PATH, the one of node with the packages installed beside it, the real directory of each program a check starts); the operation gets the environment of the profile only (`HOME` and the temporary directory are in the directory of the run, so the tests no longer write `~/.prd-gen`). Before anything runs, a canary under each profile tries a write in the worktree, the git directory, the files of the gate, the home and a directory outside, each write and read the profile denies, and, for `offline`, a port of the host; one success, or a canary that does not say that every attempt was refused, and the gate refuses to run, with no unsandboxed fallback. The runtime and the operation get a PATH without any entry of the judged tree or of the run, and without relative entries. A check passes when its command ran to its end with status 0, which the gate reads from a mark the command leaves, since the sandbox runtime exits 0 when its command is ended by a signal. The gate runs git found on PATH outside the judged tree, links followed, from the root of the worktree, and the sandbox runtime installed in the main checkout, or in the worktree when the main checkout has none, by its path; what it reads back from the copy (a source, the mutation report) is refused when a link leads outside the copy, a link put in place of the copy included. Stryker's copy of the project leaves out `.mcp.json` and `.claude`, which the sandbox runtime lets no operation write. (2) `pnpm gate:install` puts a pre-push hook in the git directory: git gives it the tip of each ref a push sends, and it refuses a tip whose tree has no passed verdict (a commit below the tip is not judged on its own); it names node and git by their paths and sets its own PATH. The gate that judges and the gate that reads the verdict is the one of the base revision (`origin/main`) as git has it, not a file of a checkout: `pnpm gate` takes it out of git and hands the run over to it, and the hook, which no commit reaches, does the same with the revision it was installed with, which must be a branch of a remote that has the gate; where that revision has no gate the hook refuses the push, and it never reads a gate from a checkout. So, with the hook installed, a commit that changes the gate, in a worktree or in the main checkout, is judged by the gate it replaces, and the verdict of the gate it brings is refused at the push. While the base has no gate, `pnpm gate` lets the gate of the checkout judge and the hook cannot be installed. (3) In Claude Code, the `PreToolUse` hook of the new `.claude/settings.json` runs `gate.mjs hook` before every tool that carries a command: it refuses a push while the pre-push hook is not the one git will run (absent, another one, not executable, or `core.hooksPath` set), what a rule of `guard.refuse` names with its reason (`--no-verify` on a push, setting `core.hooksPath`, `send-pack`, a forced push, `gh pr merge`, a write to refs, contents, pulls or merges through `gh api`, `curl` to the GitHub API). The guard reads the commands of what a tool hands to a shell, not the text they carry: a quoted string and a here-document are left out, a command substitution inside a string is read as commands of its own, and `push` counts when it is git's subcommand, so a review comment or a commit message that names a refused command is not refused, written as `"$(cat <<'EOF' … EOF)"` included. It also refuses the GitHub tools that send content from their input; in a session on a hosted runner or in a cloud session (`guard.hosted`: `GITHUB_ACTIONS`, `CLAUDE_CODE_REMOTE`), where a checkout has no hook and no verdict, a push is let through and the refusals still hold, so the routines that deliver from there keep delivering, judged by the Pipeline and not yet by mutation testing; a call made from a directory that is in no repository is guarded like one made from the project, one made from inside another repository is not; a configuration it cannot read, a crash of the guard, a gate file moved aside or a missing `node` blocks every guarded call, and a checkout whose commit has no gate is not guarded. The same file is the one permission file of the repository, with no personal copy beside it: it allows `pnpm gate` alone without asking, and denies what the CI contract forbids without condition (`git merge-base`, `gh pr update-branch`, a forced push, a push with `--no-verify`, a merge by hand), the reading of secrets, and those GitHub tools. `.claude/skills/deliver/SKILL.md` gives the procedure, with one fresh subagent per reviewer of `.claude/agents/`. The decisions are in `gate-lib.mjs`, tested with doubles and inside the gate's own mutation perimeter; `gate.mjs` holds the adapters and is tested as a program (a real repository, a real push, and a run with a stand-in for the sandbox runtime); the sandbox runtime is not started by the test suite, the gate proves it each time it runs. What this gate does not hold against is listed in CONTRIBUTING.md, "The delivery gate": a verdict written by hand or a base revision moved on purpose, a command written to escape the guard's expressions, a test suite that lies, dependencies that are not those of the lockfile, a change that only deletes lines; the hosted Pipeline, which is what holds against the first of these, does not run the mutation testing yet (a key of `ci.json` enters after the validator accepts it). Measured on this repository: mutating 16 changed files whole took 10 minutes 11 seconds for 1,702 mutants, of which 123 touched a changed line; copying `node_modules` (391 MB, 23,703 files) into the directory of a run took 42 seconds. Found by the first run in that directory, and fixed: the guard of `scripts/tests/test_frozen_baseline_is_provenance.py` skipped a file when any directory of its whole path was named `dist`, `.git` or `node_modules`, so a checkout that lives under such a directory was not read at all and the guard passed on anything; the names are now read below the scanned root only, with a test.

- `validate_prd_document` reports a new document-level rule, `consistent_control_names` (#118, seeded defect `inconsistent_terminology`). The named controls of the requirement definitions (`FR-n`, `NFR-n`) and of the acceptance-criterion definitions (`AC-n`), read with the block tree of `measurable_requirements`, are compared: a named control is a capitalized word next to a noun of a new bilingual lexicon concept, `controlNouns` (EN: button, control, link, toggle, switch, checkbox, dropdown, menu, tab, icon; FR: bouton, contrôle, lien, interrupteur, menu, onglet, icône; with their plurals), before the noun in English (`Copy button`, `"Copy" button`) and after it in French (`bouton Copier`, `bouton « Copier »`). An acceptance criterion that names a control whose name no requirement uses is reported: `1 acceptance criterion(s) name a control no requirement names: AC-001 ("Clone control")`. Names are compared case-insensitively and the noun is not compared, so `Copy control` matches `Copy button`; determiners (`The button`, `Le menu`), lowercase and hyphenated words and code spans are not names; when no requirement names a control nothing is reported. Source: the "consistent" characteristic of a set of requirements in ISO/IEC/IEEE 29148:2018 (terms used consistently). The finding is blocking but not critical (penalty 0.05, no critical retry), because what is a name is a heuristic. The pattern stays linear on long words, space runs and quote runs (`regex-hardening.perf.ts`). The seeded `inconsistent_terminology` defect is now diagnosed, so the recall of the rebuilt set is 8 of 10.
- `validate_prd_document` reports a new document-level rule, `contradictory_requirements` (#118, seeded defect `contradiction`). Two requirement definitions (`FR-n` or `NFR-n`, read with the block tree of `measurable_requirements`; the statement is the first cell of a table row) contradict each other when their statements are the same word for word but for their numbers, and every number that differs is a quantity: followed by a unit of measure of the new bilingual lexicon concept `quantityUnits` (seconds, minutes, MB, %, fois…; EN and FR, a plural read by its final s). A count noun (`users`, `files`, `steps`), a word that is also a verb (`times`, `attempts`, `clicks`, `requests`) and a unit of one language that is a common word of the other (`to`, `go`, `an`, `o`) are not units: they follow a number that names as often as one that counts, so `Tier 1 users can export CSV.` against `Tier 2 users …`, `Version 1 to 3 …` against `Version 2 to 3 …` and `Step 1 times out …` against `Step 2 times out …` are not reported, and neither is `10 users` against `50 users` (review 1 of #318, note 1). The later one is reported: `1 requirement(s) state a quantity an earlier requirement states differently: FR-004 ("five", against FR-003: "two")`. A number that names rather than measures (`Tier 1`, `Step 2`, `FR-001`) is not followed by a unit, so two statements that differ there are not reported; `two` and `2` are one value, and so are `1,000` and `1000`: a comma, or a repeated separator, followed by groups of three digits groups thousands, the last of two kinds of separator is the decimal mark, and a form that reads as no number (`1.2.3`) is its own value, where every `1,000,000`-style number read as `NaN` and all of them as equal (review 1 of #318, note 1); a reused identifier is left to `duplicate_requirement_ids`. Source: ISO/IEC/IEEE 29148:2018 §5.2.6 (a set of requirements is consistent). The finding is blocking but not critical (penalty 0.05, no critical retry): it sees only a contradiction of identical wording. Each requirement is compared with the first one of its form only, so the cost is linear (superseded by the follow-up of #330 review: with at most three earlier ones of its form, the first, the first that measures the same numbers and the first that measures all of them); every later one is compared, so a requirement that comes after a reused identifier, or that states the value of one already reported, is reported too (review 1 of #318, note 2). A quoted spelling longer than 24 characters is cut and ends with `…`. The seeded `contradiction` defect is now diagnosed, so the recall of the rebuilt set is 7 of 10.
- `validate_prd_document` reports a new document-level rule, `testable_acceptance_criteria` (#118, seeded defect `untestable_statement`). An acceptance-criterion definition (`AC-n` as the first cell of a table row, or opening a list item, heading or bold line, read with the block tree of `measurable_requirements`) whose text, quoted text and code spans removed, states how a person feels is reported: `1 acceptance criterion(s) state how a person feels, which no test can observe: AC-003 ("love")`. The terms are a bilingual lexicon concept, `untestableOutcomeTerms` (EN: love, enjoy, delighted, appreciate, pleased, frustrated, annoyed; FR: adore, aime, apprécie, ravi, frustré, agacé, with their inflections), matched as whole words; words with a testable sense in a criterion are left out (like, prefer, satisfied, happy, feel). Source: ISO/IEC/IEEE 29148:2018 §5.2.5 (verifiable) and §5.2.7 (subjective language). The finding is blocking but not critical (penalty 0.05, no critical retry), because the term list is a heuristic. The reader of requirement definitions now takes the identifier prefixes as a parameter (`FR` and `NFR` by default, unchanged for `measurable_requirements`). The seeded `untestable_statement` defect is now diagnosed, so the recall of the rebuilt set is 6 of 10.
- `validate_prd_document` reports a new document-level rule, `measurable_requirements` (#118, seeded defect `unmeasurable_requirement`). A requirement definition (`FR-n` or `NFR-n` as the first cell of a table row, or opening a list item, heading or bold line) whose text, with the lines that go on with it (a heading's body up to the next heading; a list item's lines up to a blank line, a heading, a table row or a list item not nested under it), holds an unbounded quality term and no number is reported: `1 requirement(s) state an unbounded quality with no number: FR-004 ("fast")`. The terms are a bilingual lexicon concept, `unboundedQualityTerms` (EN: fast, quick, user-friendly, easy, intuitive, seamless, efficient, robust, if possible, as needed, minimal, significant, optimal…; FR: rapide, convivial, facile, fluide, efficace, si possible, au besoin…), taken from the unbounded and ambiguous terms of ISO/IEC/IEEE 29148:2018 §5.2.7, matched as whole words (a hyphen is part of a word, so `fast-track` and `Breakfast` are not read). A number in digits, or a number word other than "one" / "un" (EN or FR, compounds read by their parts: `twenty-five`, `dix-sept`), counts as the bound; the rule does not check that the number belongs to the term. Quoted text and code spans (`"Fast mode"`, `` `quickSort` ``) are not read, with a quote body that excludes its opening mark so a line of unclosed `“` or `«` stays linear (`regex-hardening.perf.ts`); fenced blocks are skipped; each identifier is named once. The finding is blocking but not critical (penalty 0.05, no critical retry), because the term list is a heuristic. The seeded `unmeasurable_requirement` defect is now diagnosed, so the recall of the rebuilt set is 5 of 10.

- `sp_arithmetic` reads the prose total of a user-story list (#118, seeded defect `wrong_number`). In the `user_stories` section, the list items that carry a story-point amount (`- STORY-1: … — 2 SP`) are summed and compared with the one line that starts with Total, Sum, Subtotal or Grand Total, after an optional bullet, ordinal or emphasis, and carries an amount (`Total: 5 SP`, `**Total:** 5 SP`, `3. Total — 5 story points`); a difference is a blocking finding, `SP total line shows 5 but the stories sum to 3`, reported once by the document check. Only the list items above the total are summed, so a `Deferred` list under it is not counted, and only the shallowest of them, so a story broken into indented tasks counts once; an emphasized amount (`**1** SP`) is read; table rows stay with the table check; fenced blocks are skipped; a total without an `SP` or `story points` unit is not read. Nothing is reported, rather than a guess, with several total lines (a subtotal per epic) or when a story's amount is not on its first line. The total-line pattern has no two adjacent whitespace loops, so it stays linear on a long line of spaces (`regex-hardening.perf.ts`). The seeded `wrong_number` defect is now diagnosed, so the recall of the rebuilt set is 4 of 10.

  The release procedure deprecates all versions of the former Registry entry
  only after the new canonical entry is active.

- **Portable Spec Verifier for Codex and Gemini CLI.** Both host manifests now
  launch the same opt-in `verifier` profile, which advertises and accepts only
  `validate_prd_section` and `validate_prd_document`. The shared `audit-prd`
  and `validate-spec` skills preserve the boundary between deterministic
  structural conformance and semantic or factual correctness. The existing
  Claude manifest still selects no profile, so its default 17-tool `full`

### Fixed

- **Registry checksum guard now validates the field consumers actually read.**
  Release automation and verification use the schema-defined `fileSha256`
  property rather than agreeing circularly on an unused `file_sha256` field.
  The checksum is omitted until the artifact exists, and both identity and
  digest guards explicitly reject the former all-zero placeholder.

- **Codex and Gemini verifier startup from immutable plugin installs.** Their

  remaining Claude launcher after the portable hosts stopped invoking it.

- **The server advertised the wrong version to every host that connected.**
  `serverInfo.version` was the literal `0.4.0` in `packages/mcp-server/src/index.ts`
  while package.json, `.claude-plugin/plugin.json`, manifest.json and server.json
  all carried `0.6.1` — three releases of drift, read by every MCP client at
  handshake and by the registry entry built from it. The number is no longer
  written down twice: `server-version.ts` resolves it at startup from the
  package.json that ships beside the running bundle (the plugin tree and the
  staged .mcpb both carry `mcp-server/package.json`), falling back to the root
  package.json for workspace runs, and returning an obviously-unresolved
  sentinel rather than a plausible-looking number if neither can be read.
  `pnpm bundle` stamps `mcp-server/package.json` from the root version
  (`scripts/stamp-bundle-version.mjs`), and CI's bundle-freshness check now
  diffs all of `mcp-server/`, so an unstamped commit fails.

  The gate that should have caught this is fixed too: `smoke-mcpb.sh` printed
  `serverInfo.version` in its OK line while asserting only that a serverInfo
  existed, so the wrong version passed CI in green for three releases. It now
  asserts the advertised version equals the one manifest.json declares — two
  independent mirrors of the release, so the check can actually fail.
